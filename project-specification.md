**Version:** 3.7

**Purpose:** This document is the authoritative technical reference for Alpha Bot. It must be provided as context at the start of any development session. All architectural decisions are final unless explicitly revised in Section 17 (Change Log).

## 1. Project Overview

### 1.1 Purpose
An automated escrow system operating via a Telegram bot (Alpha Bot), facilitating professional peer-to-peer exchange of USDT (BEP20) for Syrian Pounds (New SYP) through local payment rails (Sham Cash SYP, Syriatel Cash, Al-Haram Bank Transfer, Al-Fouad Bank Transfer). The system acts as a trusted intermediary that holds USDT custody during the transaction lifecycle.

### 1.2 Core Design Principle: Efficiency & Professionalism
- **Per-deal address isolation**: Unique blockchain deposit address per transaction.
- **New Syrian Lira Scale**: The system operates on the New Syrian Lira scale (1 Old Lira = 100 New Lira). Users enter rates like 145 instead of 14,500.
- **Professional Microcopy**: Strict adherence to formal, professional Arabic. No informal Syrian Lira references or wordy clichés.

### 1.3 Scope of This Document
This document covers system architecture, data model, security requirements, and operational requirements. It does not cover UI copy, marketing, or legal/regulatory compliance — those are handled separately and are prerequisites to production deployment, not engineering concerns.

## 3. System Architecture

### 3.1 Service Decomposition
The system is composed of three independently-deployed services, not a monolithic script:

| Service | Responsibility | Failure Isolation Rationale |
|---|---|---|
| **Bot Service** | Telegram update handling, conversation state (FSM), user-facing command logic | Must remain responsive to users independent of chain monitoring load |
| **Chain Watcher** | Continuous polling of active deposit addresses, deposit confirmation, triggers state transitions | Must run independent of bot responsiveness; a chain-monitoring failure must not silence the bot |
| **PostgreSQL Instance** | Single source of truth for all deal, user, and audit state | Decoupled from application logic; backed up independently |

### 3.2 Inter-Service Communication
Both Bot Service and Chain Watcher read/write to the same PostgreSQL instance. No direct service-to-service RPC is required for MVP; polling-based coordination via DB state is sufficient at expected transaction volume.

### 3.3 Wallet Architecture: HD (Hierarchical Deterministic) Derivation
- A single master seed is generated once, at system initialization, via a cryptographically secure process (offline generation recommended, not generated by the running server).
- Each deal is assigned a unique `deposit_index` generated via an independent PostgreSQL SEQUENCE (`deposit_index_seq`), completely detached from `deals.id`, via `nextval('deposit_index_seq')` on deal creation. Separating `deposit_index` from `deals.id` prevents implicit disclosure of aggregate platform deal volume and maintains full separation between the cryptographic security derivation identifier and the internal commercial record ID. The `deposit_address` remains mock-generated (`0x_mock_...`) until Phase 2 as planned.
- The deposit address and its corresponding private key are derived per-deal via standard BIP-32/BIP-44 derivation path (e.g., `m/44'/60'/0'/0/{deposit_index}`).
- Fund release to the buyer is signed directly from the derived deal address — no intermediate consolidation/sweeping step is required for MVP.

**Operational dependency:** Each derived address requires a small BNB balance to cover gas fees on release. This requires either (a) a pre-funding step at address generation time, or (b) a "gas station" pattern where a funding transaction precedes each release (see Section 10).

## 4. Transaction State Machine (v3.4)

```
[Offer created by maker — Duration expiry leads to immediate deletion]
  ↓ (taker presses "start deal" and submits amount)
PENDING_OWNER_APPROVAL
  ↓ (owner or admin approves within 30 mins)
  → EXPIRED: Rule 4 — Unresponsive maker for 30 mins -> Deal cancelled AND Offer deleted
CREATED
  → AWAITING_USDT_DEPOSIT (15-min window)
    → EXPIRED: Rule 2 — No deposit for 15 mins -> Deal cancelled AND Offer reverts to ACTIVE
  → USDT_DEPOSITED
  → AWAITING_SYP_PAYMENT (30-min soft window)
    → Warning: Rule 3 — If > 30 mins, buyer must contact support before paying. Deal remains ACTIVE.
    → SYP_PAYMENT_SENT (Mandatory photo proof submission by buyer)
  → ADMIN_APPROVAL (Atomic transition post-seller receipt confirmation)
  → COMPLETED
```

### 4.0 Owner Approval & Mandatory State Outcomes (v3.4)
- **Rule 1 (Offer Expiry):** When an active offer's duration expires without active applicants, it is **deleted immediately** from the channel and database.
- **Rule 2 (USDT Deposit Timeout):** If the seller fails to deposit USDT within 15 minutes of approval, the deal is cancelled. The offer is reverted to `active` status in the market. Admins receive an alert with party IDs.
- **Rule 3 (SYP Payment Soft Timeout):** If the buyer takes more than 30 minutes to send SYP, the deal remains active (reserved), but the buyer is warned to contact support (`@AlphaSupport`) before proceeding with the transfer.
- **Rule 3b (SYP Receipt Confirmation 30-Min Reminder & Admin Alert):** Once the buyer attaches the SYP payment screenshot (`SYP_PAYMENT_SENT`), a 30-minute confirmation window (`expires_at = now + 30m`) starts. If the seller does not confirm receipt within 30 minutes, the deal remains safely open (`expires_at` cleared to `None`), the seller receives a one-time confirmation reminder, the buyer receives a reassurance update, and all `ADMIN_IDS` receive an immediate alert with a direct deal inspection button (`adm_inspect_deal_`).
- **Rule 4 (Approval Timeout):** If the offer owner fails to approve/reject a deal request within 30 minutes, the deal is cancelled AND the offer is **deleted** for non-responsiveness.
- **Cancellation Restriction:** The offer owner cannot cancel the deal once approved (in `CREATED` or `AWAITING_USDT_DEPOSIT` states). If no deposit is made, the deal expires automatically.

### 4.1 Dispute handling: Reporting Non-Receipt & Immediate Bot-Side Closure (v3.7)
The button **"⚠️ لم أستلم"** (`dispute_deal_`) allows the seller to report non-receipt of the local SYP transfer:
1. Deal status transitions to **`DISPUTED`**, which is treated as a **terminal state on the bot** (excluded from `/continue` active deals and from the 5-active-deals user cap, and included in the closed statuses of `uq_open_deal_per_offer`).
2. The associated offer is closed (`offer.status = 'cancelled'`) and removed from the public channel so it does not remain stuck in `reserved` or get re-activated by the orphan watcher.
3. A `Dispute` record is persisted for `/disputes`, and both parties + all admins receive a formal closure notice routing the case to manual resolution via `@AlphaSupport`.

### 4.2 Deposit Window Expiry Policy (revised in v2.6 / v3.4)
Deals in `CREATED` or `AWAITING_USDT_DEPOSIT` (before funds enter escrow) expire automatically **15 minutes** after entering `AWAITING_USDT_DEPOSIT` if no on-chain deposit is detected. This matches the validity window of the temporary deposit address.

**Late deposit handling:** Expiry stops the deal from progressing automatically, but the deposit address remains monitored for at least 24 hours. If a deposit arrives post-expiry, Chain Watcher flags it for manual admin intervention.

### 4.2.1 Overall Deal Timing Ceiling
Independent of the 15-minute deposit window, a deal has an overall soft ceiling of **1 hour** from creation. It is non-enforcing (does not auto-cancel) and serves as an operational signal for admin review.

### 4.3 Admin Notification Trigger & Atomic Confirmation (v3.3)
The happy-path progression `AWAITING_USDT_DEPOSIT → USDT_DEPOSITED → AWAITING_SYP_PAYMENT → SYP_PAYMENT_SENT → ADMIN_APPROVAL` requires no admin action until `ADMIN_APPROVAL`.

**Atomic Transition:** When the seller presses "Confirm SYP Receipt" (`man_conf_`), the deal transitions **atomically and directly** from `SYP_PAYMENT_SENT` to `ADMIN_APPROVAL`. The separate manual `SYP_PAYMENT_CONFIRMED` state is removed. An alert is instantly dispatched to all `ADMIN_IDS`.

**Admin `/my_deals` View:** For users in `ADMIN_IDS`, executing `/my_deals` surfaces deals in `ADMIN_APPROVAL` state first, followed by their personal deals.

### 4.3.1 Unified Interactive Deal Card (v3.3)
Each deal counterparty receives a dedicated interactive card (`deals.seller_card_msg_id` / `deals.buyer_card_msg_id`). Upon state transitions or turn handoffs, the system updates the message in-place or re-sends it with a notification alert, rendering current step, turn status, countdown timer, and contextual action buttons.

### 4.4 Offer-Level Expiry Policy, 3-Stage Duration Picker & Orphan Safety Net (v3.7)
An **offer itself** (before any deal is requested against it) has a maker-defined validity period configured during Step 8 of the Offer Creation Wizard:

**Duration Options (3-Stage Button Picker):**
- **Stage 1:** Default `4 hours` (`dur_default_4`) OR Custom Duration (`dur_custom`).
- **Stage 2 (Custom Hours — 2×2 Grid):** `0`, `1`, `2`, or `3` hours (`dur_hr_0` .. `dur_hr_3`).
- **Stage 3 (Custom Minutes — 2×3 Grid):** `5`, `10`, `15`, `20`, `30`, or `45` minutes (`dur_min_5` .. `dur_min_45`), plus `0` additional minutes (`dur_min_0`) when hours > 0.
- Valid range: `5 minutes` (`5/60` hours) up to `4 hours` (`4.0`). Formatted uniformly in Arabic across the wizard summary, publish confirmation, and channel broadcast via `format_duration_hours_minutes` (e.g., `1 ساعة و 5 دقيقة`, `30 دقيقة`, `4 ساعات`).

**Immediate Deletion on Expiry (No Grace Period):**
When an `active` offer's `expires_at` timestamp elapses without an active applicant, the background task in `bot/tasks.py` transitions its status directly to `deleted`, removes its public channel post, and notifies the offer maker.

**Orphan Offers Safety Net (v3.3+):**
If an offer is stuck in `reserved` or `negotiating` status without an active deal (`deals.status NOT IN ('CANCELLED','EXPIRED','COMPLETED','DISPUTED')`) or open negotiation (`negotiations.status IN ('PENDING_MAKER','PENDING_TAKER')`), and more than **10 minutes** have passed since `offers.status_changed_at`, a background task in `bot/tasks.py` automatically reverts `offers.status` to `"active"` and updates the channel message.

## 6. Security Requirements (Non-Negotiable)

1. **Master seed custody.** Seed stored securely with OS-level restrictions or secret manager.
2. **On-chain deposit verification.** Every `USDT_DEPOSITED` transition backed by BscScan / RPC query.
3. **SYP payment confirmation (mutual, non-verified).** Two-party mutual acknowledgment with accepted risk note (Section 9.1).
4. **Input validation.** Validating amounts, BEP-20 addresses (EIP-55), and payment info.
5. **Rate limiting.** Dual-layer limits on offer creation, deal initiation, and negotiations (Section 6.1).
6. **Access control documentation.** Maintaining explicit records of production access.

## 6.1 Rate Limiting Policy (v3.3)

The system enforces two independent protection layers against spam and automated abuse:

### 6.1.1 — Active Elements Fixed Ceiling:
- **Active Offers per user:** Maximum 5 (`offers.status IN ('active', 'reserved', 'negotiating')`).
- **Active Operations per user (Deals & Negotiations):** Maximum 5 (`deals.status NOT IN ('COMPLETED', 'CANCELLED', 'EXPIRED', 'DISPUTED')` + `negotiations.status IN ('PENDING_MAKER', 'PENDING_TAKER')`).
- Applies to **both counterparties (Maker & Taker)**.

### 6.1.2 — Rolling Time Window:
- **Offer Creation:** Maximum 3 attempts per 10 rolling minutes.
- **Deal & Negotiation Initiation:** Maximum 5 attempts per 10 rolling minutes.

### 6.1.3 — Execution & Locking Rules:
- **Entry point pre-check:** Validated immediately upon user interaction (`/create_offer`, `start_deal_`, `start_neg_`).
- **Atomic re-check under lock:** Mandatory re-check under `SELECT ... FOR UPDATE` row lock on `User` / `Offer` during actual persistence or state conversion.
- **Admin Exemption:** Accounts in `settings.ADMIN_IDS` are exempt.

## 9. Fraud Mitigation & Proportional Dual Fee Model

| Risk | Control |
|---|---|
| False "USDT sent" claims | On-chain verification (Section 6 item 2) |
| False "SYP sent/received" claims | Accepted risk, mutual acknowledgment (Section 9.1) |
| Wash trading | Minimum deal sizes and percentage reputation tracking (0%–100%) |
| Unilateral post-custody cancellation | State-machine invariant — post-`USDT_DEPOSITED` requires admin intervention |
| Address reuse | Per-deal unique derivation (Section 3.3, 5.1) |

### 9.1 Proportional Dual Fee Model
The proportional fee model ensures fairness across transaction sizes:
- **Free Tier:** Transactions ≤ **25 USDT** incur **zero** platform fees for both parties.
- **Standard Fee:** Transactions > **25 USDT** incur a fee of **0.1%** (`1/1000`) per counterparty.
- **Seller Portion:** Seller deposits `amount_usdt + fee` into escrow.
- **Buyer Portion:** Buyer receives net `amount_usdt - fee` upon release.
- **Calculation Rule:** `fee = amount_usdt * 0.001` (quantized to 6 decimals).

### 9.2 Accepted Risk Note — SYP Payment Confirmation
Confirmed by mutual acknowledgment. Re-introducing reference validation remains possible via `payment_proofs` without DB migration.

## 12. Negotiation System (v2.7 / v3.3)

Offers may optionally enable negotiation (`offers.negotiable_type`: `none` | `amount` | `rate` | `both`).

**State Machine:**
Managed via `negotiations` table. Statuses: `PENDING_MAKER` → (maker accepts | maker counters → `PENDING_TAKER` → taker accepts | taker rejects) | maker rejects | 30-minute timeout → `EXPIRED`. Maximum 1 counter-offer round.

**Offer Locking & Proposal Submission:**
When the taker submits a negotiation proposal, the offer status flips to `negotiating` (excluded from `/offers` and channel). On rejection, expiry, or cancellation, the offer reverts to `active`.

**Privacy-by-Design Payment Flow (v3.6+):**
During Offer Creation (Step 6), the maker privately provides payout details (`offers.payout_details`): a `USDT (BEP-20)` address for buy offers, or per-method local receiving accounts for sell offers. These details are never exposed in the public channel or `/offers`. When a deal is initiated or a negotiation is accepted, the corresponding payout account is automatically linked (or selected by the buyer via `nego_pm_` if multiple payment rails are enabled on a sell offer).

**Operational Admin Intervention:**
Admin accounts (`settings.ADMIN_IDS`) can execute approval/rejection/counter-offer actions (`neg_m_acc_`, `neg_m_rej_`, `neg_m_cnt_`, `neg_t_acc_`, `neg_t_rej_`) on behalf of stalled parties.

## 14. System Resilience, Bot Commands & Production Hardening (v2.9 / v3.9)

1. **Smart Critical Error Alerting (`error_alert.py`):** Deduplicated alerts dispatched to admins with deep project-frame traceback extraction (filtering out `site-packages` frames to pinpoint the exact project handler line); full logs written to `escrow_system.log`.
2. **Connection Pool & Statement Timeout Resilience (`db/session.py`, `bot/main.py`):** `pool_pre_ping=True`, `pool_recycle=1800`, `pool_timeout=30`, `connect_args={"command_timeout": 30}` for asyncpg to prevent hung SQL statements or deadlocked `FOR UPDATE` rows, plus automatic `session.rollback()` inside `DbSessionMiddleware` on unhandled exceptions.
3. **Self-Healing Polling Supervisor & Background Watchdog (`bot/main.py`, `bot/tasks.py`):**
   - Outer supervisor loop (`while True` with exponential backoff up to 60s) around `AiohttpSession(timeout=30)` and `dp.start_polling(bot, polling_timeout=20)` so network drops or Telegram server stalls never terminate or freeze the bot.
   - `supervise_background_workers` watchdog checks `start_expiry_watcher` and `start_daily_backup_scheduler` every 30s and automatically respawns either task if it ever exits unexpectedly, with `asyncio.wait_for(..., timeout=120)` execution bounds on each cycle.
4. **Non-Blocking Daily Automated Backup (`bot/services/backup_service.py`):** Exports all 10 tables (including `deal_ratings`, `payout_details`, `seller_fee_usdt`, `buyer_fee_usdt`), offloads JSON serialization, gzip compression, and 30-day rolling disk retention in `/backups/` to a worker thread via `asyncio.to_thread`, and dispatches the `.json.gz` file to all `ADMIN_IDS` daily at `00:00 UTC`.
5. **Rate-limited Broadcast & Safe Entity Escaping:** Strict Markdown (`escape_markdown`, `safe_username`) and HTML (`html.escape`) escaping across all user inputs, usernames, support handles, dispute reasons, and feedback notes.
6. **Seamless FSM Interruption (`command_cancel.py`):** Intercepts slash commands and clears stale dialog state.
7. **Official Bot Menu Commands & Deep Linking (`bot/main.py`, `bot/handlers/base.py`):**
   - `/start`: Main menu and deep-link router (`?start=offer_<id>` for direct offer interaction, `?start=offers` for opening the market browser from channel cards, and `?start=ref_<id>` for referrals).
   - `/continue`: Resumes the user's active deal by re-sending the live interactive deal card while automatically deleting previous card messages (`seller_card_msg_id` / `buyer_card_msg_id`) to prevent stale duplicate buttons; also surfaces pending owner approvals and active negotiations.
   - `/support`: Displays the unified technical support card (`@AlphaSupport`) with instructions for submitting inquiries or dispute evidence.

## 15. User Profile, Offer Creation Wizard & Loyalty System (v3.0 / v3.9)

1. **Profile Card & Post-Deal Star Rating System (`deal_ratings`, `bot/services/rating_service.py`):** Trader badge, completed deal count, and `reputation_score` on a `0%–100%` percentage scale (default `100%`). Immediately upon deal completion (`COMPLETED` via `man_rel_`), both buyer and seller receive a one-tap 1–5 star rating card (`rate_deal_<deal_id>_<stars>`), strictly enforced once per party per deal via `uq_rating_per_deal_rater`, updating `users.reputation_score` automatically (`ROUND(AVG(stars) * 20)`). Admins can inspect and delete erroneous ratings directly from `/deal [id]` (`adm_del_rating_`) or from the user's dossier `/user` (`adm_user_ratings_`), triggering automatic reputation recalculation and `DELETE_RATING` audit logging.
2. **Offer Creation Wizard UX (`bot/handlers/offers.py`, `bot/utils/offer_wizard.py`):**
   - **Progressive Draft Header (`format_wizard_draft_header`):** Displays accumulated choices (`offer_type`, `rate`, `min_limit`, `max_limit`, `payment_methods`) at the top of each wizard step.
   - **2×2 Payment Methods Grid (`get_payment_methods_kb`):** Arranges the 4 approved payment methods in a clean 2-column grid.
   - **Saved Rails Validation & Confirmation Gate:** Validates saved BEP-20 wallet (`users.saved_usdt_address`) and method-specific local payment accounts (`users.saved_payment_info`) before offering one-tap reuse.
   - **3-Stage Custom Duration Picker:** Buttons for Default (`4 hours`) or Custom (`0–3 hours` × `5–45 minutes`).
   - **Final Summary & Jump-Edit:** Full summary screen (`format_wizard_summary`) with individual jump-edit buttons (`✏️ السعر`, `✏️ الكمية`, `✏️ الدفع`, `✏️ الحساب`, `✏️ التفاوض`, `✏️ المدة`) that return directly to the summary after editing.
3. **Golden Points Loyalty Program:** Operational flag `REWARDS_ENABLED` (default `false`). Points for deals (+10) and referrals (+25). Tiered claims (500/1500/3000 pts).
4. **Approved Local Payment Methods & Validation:** `شام كاش ليرة` (32-hex address), `سيريتيل كاش` (10-digit `09xxxxxxxx` with Arabic numeral normalization), `حوالة بنكية (الهرم)` & `حوالة بنكية (الفؤاد)` (full triple name + Syrian mobile number `09xxxxxxxx`).

## 16. Explicit Non-Goals for MVP

To keep scope bounded, the following are intentionally excluded from MVP:
- Multi-currency support beyond USDT/SYP.
- Multi-network support beyond BEP20.
- Automated dispute resolution (all disputes are human-adjudicated for MVP).
- Fund consolidation/sweeping to a central treasury address.
